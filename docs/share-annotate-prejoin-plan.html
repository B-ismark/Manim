Manim · implementation plan

Seven commits, ten dead-ends found before writing any of them.

A sequenced plan for all ten share/annotate findings plus the prejoin feed layout. Every commit is independently reviewable, independently revertable, and passes typecheck on its own. The dead-ends section is the part worth reading first — one of them would have silently broken every screen-share test in the suite.

The sequence

Ordered so each commit makes the next one smaller. C1 is a pure refactor with no behaviour change; it exists because nothing else can be fixed once until there is a single place that starts a share.

C1

Extract useScreenShare()

F4 · no behaviour change
  • New src/features/calls/useScreenShare.ts owning the capture options object, the CaptureController, the surface-type read and the store write.
  • Four call sites become start()/stop(): ControlBar.tsx:323, ControlBar.tsx:591, PipPanel.tsx:123, useMediaDeviceWatch.ts:94.
  • Options land here and nowhere else: selfBrowserSurface: 'exclude', surfaceSwitching: 'include', systemAudio: 'include'.

The toast’s “Share again” action (useMediaDeviceWatch.ts:94) is the call site that makes this non-optional. It’s the recovery path — a share restarted after an accidental stop would otherwise silently lose every option added in C2, and it’s the one nobody would think to test.

C7

Polish

F9 · F10
  • F9 — a one-shot pill the first time remote ink arrives on a touch device (“Name is drawing on the shared screen”), giving the existing Announcer message a visible counterpart.
  • F10 — publish the share track specifically as VP8 so contentHint: 'detail' survives. Not shipped: the finding was withdrawn. The motion-hint stomp is real, but LiveKit already cancels its consequence with degradationPreference: 'maintain-resolution' for screen shares, and so does livekit.ts. VP8 would have cost VP9’s efficiency and added a simulcast layer. See the corrected F10 in the audit.

The plan said F10 needed a real bandwidth comparison before shipping. It turned out to need one more careful read of the mechanism instead — which is the cheaper check, and should have come first.

Dead-ends and inconsistencies found while planning

These came out of reading the test harness and the surrounding stores rather than the findings themselves. D1 and D2 change how C2 has to be built; D3 changes the wire design; D7 changes which prejoin prototype we should actually ship.

D1

The test harness produces no displaySurface at all

Evidence
tests/helpers.ts:298 — fakeScreenShare overrides getDisplayMedia to return canvas.captureStream(). A canvas capture track reports getSettings().displaySurface === undefined.
Impact
Every share test in the suite — 12-resilience, 17-annotate (×4), 18-annotate-perf, 19-overlays — would land in whatever branch we assign to “unknown”. Written the naive way, C2 would either break all of them or make all of them exercise a path no real user is on. Firefox has historically omitted the field too, so this is not only a test problem.
Plan
Treat unknown as permissive (behave like a window share). A false “monitor” would remove the annotate path from every browser that doesn’t report the field, which is a worse failure than the mirror it prevents. Then extend fakeScreenShare(page, w, h, fps, surface) to stamp getSettings() so both branches become testable.
And
Because detection can’t be trusted everywhere, C2 also adds an explicit “Hide my screen from my view” toggle on the presenting pill. Whatever the browser reports, the presenter gets a one-tap fix — and we stop depending on a support matrix for a correctness property.
D2

An existing test asserts exactly the behaviour C2 changes

Evidence
tests/17-annotate.spec.ts:260 — “a presenter can draw on their own share, and only while the pen is armed”, with a comment explaining that a presenter’s own captured frame is the only surface a browser tab can draw on.
Impact
This is not a stale test. It encodes the deliberate design decision that made annotation discoverable, and deleting it would silently give that up.
Plan
Re-specify, don’t remove: keep it verbatim as the window-share case (which is what it actually exercises once D1’s surface argument exists), and add a monitor-share case asserting the presenter card, the absent echo, and a pen that is absent with a reason rather than present-and-dead.
D3

A wire bump has no negotiation — mixed clients lose all ink

Evidence
src/lib/annotate/wire.ts:82 — if (view.getUint8(0) !== WIRE_VERSION) return null. Exact match, both directions.
Impact
A call spanning a deploy has some tabs on v1 and some on v2, and ink disappears silently in both directions — no error, no announcement, just strokes that never arrive.
Plan
Make v2 decoders accept v1 packets (10-byte header vs 6, discriminated by the version byte; a v1 packet is treated as “target unknown → accept”). New clients then understand old ones. Old clients still drop v2 — asymmetric, but strictly better than mutual loss, and it self-heals on reload. Stating this cost rather than hiding it: for a few minutes after a deploy, an un-reloaded tab won’t see new ink.
D4

A sticky featured share can strand the layout

Evidence
Stage.tsx:295–297 — prunePresentation already clears demoted-share flags and a stale person-spotlight when tracks change.
Impact
C4’s sticky share key is a fourth piece of presentation state. If it isn’t pruned when that share ends, the big region holds a key pointing at nothing.
Plan
Add it to the same prune call rather than a new effect. There are already three cleanup paths here; a fourth independent one is how they drift.
D5

Taking over capture would break the stop-sharing toast

Evidence
useMediaDeviceWatch.ts:38 — localParticipant.getTrackPublication(Track.Source.ScreenShare), then an ended listener on its MediaStreamTrack.
Impact
If F3’s fallback is taken (capturing with getDisplayMedia ourselves and publishing manually), the track must be published with source: Track.Source.ScreenShare explicitly, and the screen-share audio track published alongside it. Miss either and the “Screen sharing stopped / Share again” recovery toast stops firing — the exact path D1 already flagged as the easy one to forget.
Plan
Try the controller-through-LiveKit route first (C2). Only fall back to manual capture if Conditional Focus proves to fire too late, and if so, port the ended wiring in the same commit.
D6

The prejoin aspect test selects the first <video> on the page

Evidence
tests/02-prejoin-join.spec.ts:49–51 — document.querySelector('video'), then v.parentElement as the aspect-carrying box.
Impact
Prototype D as drawn adds a blurred backdrop copy of the preview. Whichever of the two lands first in the DOM wins the selector, and the parent is no longer the box whose aspect is being asserted. The test would fail — or worse, pass against the wrong element.
Plan
data-testid="prejoin-preview" on the real preview and a selector update. Better spec regardless of which prototype ships.
D7

Prototype D’s blurred fill is a second decode — and mostly unnecessary

Impact
The blur fill exists to kill the bars when the video’s aspect doesn’t match the header’s. But if the header’s height is derived from previewAspect at full card width, a landscape camera fills it exactly — the bars never appear, and the second <video> decoding the same stream is pure cost on a low-end phone, at the moment we’re about to connect.
Revision
Drop the fill from the common case entirely. It would only be needed where the header height clamps — a portrait camera — and there, prototype E’s side-by-side pivot is the better answer anyway: a tall frame leaves a natural column that the form fills exactly.
Consequence
Ship D and E as one component, not as two variants to choose between. This is a change to the recommendation in the prototypes doc, and it came out of planning the implementation rather than drawing the mockups.
D8

Prejoin opens the microphone up to three times

Evidence
PreJoin.tsx:94 (requestAccess: video+audio), PreJoin.tsx:118 (preview: video only), PreJoin.tsx:352 (MicSpeakerTest: audio only).
Impact
Three independent getUserMedia calls with overlapping lifetimes. Concurrent mic acquisition is a known cause of a stalled preview on mobile. Not caused by the layout work, but it is squarely in C6’s blast radius — any restructure touches all three.
Plan
Consolidate to one prewarm stream that both the preview and the level meter read. Flagged, not scheduled — if it turns out to be more than a small change, it becomes its own commit rather than riding along with C6.
D9

The pen already has two disarm paths; F6 and F8 would add a third and fourth

Evidence
ControlBar.tsx:122–124 (disarm when the last share ends) and useAnnotateStore.setAllowed (disarm on permission loss).
Impact
Adding “disarm when the featured tile stops being a share” and “disarm when the canvas unmounts” as two more independent effects is how these drift out of sync — the same failure that produced useSharePresence in the first place.
Plan
One derived rule in useSharePresence() (canAnnotate), with a single effect that disarms when it goes false. C3 and C4 both consume it rather than adding their own.
D10

A demoted share has no pen, no fullscreen, and a still-enabled control-bar pen

Evidence
Stage.tsx:755–760 — FullscreenControls, AnnotateControl and AnnotationOverlay all render only inside PresentationStage, gated on bigIsShare.
Impact
Demote a share to the grid (toggleShareDemoted) and it keeps a “Present shared screen” button, loses fullscreen and the pen — correct — while the control bar’s pen stays lit. Three surfaces, three different ideas of what “the share” currently is.
Plan
C3’s shareFeatured is the single answer all three read. No new behaviour — just one concept instead of three implicit ones.

Four calls I’d like confirmed

Everything else in this plan I’ll just make. These four change what users experience, so they’re yours. My recommendation is on each — say nothing and I’ll take it.

1 · What does an unknown displaySurface mean?

Browsers that don’t report it (and the test harness) give us no answer. Permissive keeps annotation working everywhere but leaves the mirror possible on those browsers; safe kills the mirror but removes the pen for users who could have had it.

Recommend: permissive, paired with the explicit “Hide my screen from my view” toggle so the presenter is never stuck either way.

2 · Can you annotate your own full-screen share?

Physically you can — you’d be drawing on a mirror, which is what produces the doubled cursor. Teams and Zoom solve this with an OS-level overlay a browser tab cannot have.

Recommend: no, with a stated reason — “Annotation isn’t available while sharing your entire screen. Share a window or tab to draw.” An explained absence beats a control that works badly.

3 · Is the asymmetric wire bump acceptable?

New clients would understand old packets; old clients would drop new ones until the tab reloads. The alternative is carrying both versions on the wire indefinitely.

Recommend: accept it. Ink is ephemeral and fades in ~4s, so the worst case is a few minutes of missing strokes for someone who hasn’t reloaded since the deploy.

4 · Prejoin — D+E merged, or C6a alone first?

C6a (footer compression) fixes the real defect and is a small, safe diff. C6b is the bigger visual change and, per D7, is now D and E as one component rather than a choice between them.

Recommend: both, as two commits. C6a lands and can be judged on its own; C6b follows on top and is revertable without losing the fix.

Two things this plan deliberately does not do

It doesn’t touch the annotation hot path. AnnotationEngine owns all stroke data outside React by design, and its header says to read it before changing anything. C4 changes the wire format and the overlay’s cleanup — it does not move a single point into state.

It doesn’t widen prejoin into the split-stage layouts (prototypes A or B). Both are viable and B is the most striking, but B needs a STYLE.md §2 amendment and a full a11y re-run for chrome sitting on video. That’s a lot to spend before C6a proves the space problem is actually solved.
